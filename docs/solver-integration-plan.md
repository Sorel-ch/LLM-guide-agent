| 版本 | `requires_python` | Windows wheel |

| 0.14.1（demo 现用） | `>=3.11` | cp311–cp315 |

所以「必须升级到 3.12」这个约束不存在，代价只是 API 降级（§3）。

## 3. 降级代价（0.11.3 vs 0.14.1，已对着 `.pyi` 与 `Model.py` 实测）

| 项 | 0.14.1（demo 现用） | 0.11.3（3.10 可用） | 影响 |
|---|---|---|---|
| `Model` | 在 `_pyvrp` 里 | **在 `Model.py`（Python 层）** | 存在，签名一致 |
| `add_location()` | 有 | **没有** | `add_client/add_depot` 直接收 `x,y` |
| `add_depot(x, y, ...)` | 收 `Location` | **收 `x: int, y: int`** | 见下 |
| `add_client(...)` | `location=` 关键字 | **`x=, y=`** | 调用点改写 |
| `add_vehicle_type` | `shift_duration=` | **`max_duration=`** | 改关键字名 |
| `add_client_group` | 有 | **有**（`required=True`） | 不变 |
| `Result`/`schedule()`/`is_feasible()` | — | 全有 | 时间线打印不变 |

**坐标必须是 int**：0.11.3 的 `add_client(x: int, y: int)` 只收整数。
现有 `solve.py` 传的是 float 经纬度，必须换成「整数索引 + 距离/时长矩阵」
（PyVRP 标准的 `ProblemData` 用法），这是**降级里工作量最大的一处**，也是
接入真实车程矩阵的天然落点（§5 T3）。

改造面（`solve.py` 实测）：`add_location` 3 处、`add_depot` 1 处、`add_client` 1 处、
`add_vehicle_type` 1 处、`model.locations` 索引 5 处、`shift_duration` 1 处。

## 4. 目标架构

```
                    ┌──────── 本次新增 ────────┐
管线（主，scripts/plan_agent.py）
  澄清 → wiki → 高德/秘塔取数（景点+餐宿）
        → suggest_order() 分天      ← 选点/分天仍在这里
        → cap_day_sights() ≤3       ← 每天景点上限仍在这里
        → [可选] 求解器重排当天时序 ← 只吃「景点」，输出到达/离开时刻
        → 餐宿按空间就近插回        ← 餐宿永不过求解器
        → 补腿 / 折线 / 落盘
```

**四条硬约束**（违反即返工）：

1. **求解器不选点**。它只接受管线已选定的点集与分天结果，返回时刻表；
   不得新增、删除或跨天搬动景点。
2. **餐宿不过求解器**。餐宿的「离哪一站最近」是空间就近语义，且已有
   `lodging_center()` + 半径周边搜实现；塞进 VRP 会被当成必访问节点。
3. **必须是可选路径**。求解器不可用 / 超时 / 不可行时，管线回退到现有
   `suggest_order()` 结果，**行为与现在完全一致**，绝不因求解失败而丢方案。
4. **不新增第二条规划流程**。禁止在 `webapp/` 或新模块里再写一份调用求解器的流程，
   一律在 `plan_agent.py` 内以函数形式接入并被 `run_plan()` 调用。

## 6.6 T3 / T4 实跑结果（2026-11-13 已交付）

### T3 车程矩阵：`travel_matrix()` + `straight_estimate()`

落在 `scripts/plan_agent.py`（`leg_index()` 之后），**直接从 `leg_index()` 的实测数据取数**，
不新建第二条取数路径。口径三档，每档都带 `basis`：

| basis | 含义 |
|---|---|
| `measured:<mode>` | direction 回来的同向实测 |
| `measured_reverse:<mode>` | **借用反向实测**。direction 的 OD 是有向的，反向不保证同值（单行道、步行道、公交去返程不对称都实测存在），所以借来的值必须与实测分得开 |
| `straight_walk` / `straight_drive` | 缺口回退：≤2.5 km 按 4.5 km/h 步行，其余按 20 km/h 市区车速 |

**为什么不用 demo 的 30 km/h**：那是纯直线折算、无路况。20 km/h 更贴市区实际
（迪士尼→陆家嘴直线 18.4 km，30 km/h 给 32′，现实周末 45–55′）。

**匹配用坐标不用名字**：台账叫「宁波博物院」、模型写「宁波博物馆」这类变体，
按名字对会静默漏掉实测值、退化成折算而不自知。

测试 `scripts/test_travel_matrix.py`：**13 项全过**（0 次外部调用）。

### T4 求解器接入：`solve_day_order()` + `reorder_day_with_solver()`

**接入点**：`run_plan()` 的 json 分支，顺序是
**cap_day_sights → 求解器重排 → plan_leg_topup → build_plan_json**。

这个顺序是硬约束：

- 重排必须在 `cap_day_sights` **之后**——先裁到每天 3 站，再排那 3 站的先后；
  反过来会把已裁掉的点也排进去，等于绕过上限；
- 必须在补腿**之前**——顺序定了，补腿才知道要补哪几对相邻。

**可关闭**：环境变量 `TRAVEL_SOLVER=0`（**调用时读，不是导入时读死**），
或机器上没装 pyvrp，都自动回退到 `suggest_order()` 的原始顺序。

**回退是整份的**：任何一天求解失败就整份返回原 groups，不做部分替换——
半套顺序比不换更难排查。

测试 `scripts/test_solver_order.py`：**无 pyvrp 23/23、有 pyvrp 24/24**。

### 集成期抓到的四个真 bug（都已修并加测试）

| 问题 | 现象 | 根因 |
|---|---|---|
| 开关读不到 | 测试里改 `TRAVEL_SOLVER=0` 无效 | `SOLVER_ENABLED` 在模块导入时读死 |
| **交通段被整批吞掉** | 重排后当天一条腿都不剩 | 重建列表只收 `meal`/`hotel`，把 `transit` 丢了 |
| 腿的 OD 错配 | 出现「午餐→老外滩」把餐厅当起点 | 重写 OD 时没按"紧邻前一个实体"取起点 |
| 末段起点错 | 「月湖→酒店」但末尾景点其实是老外滩 | 收尾回宿那条腿的起点没跟到新末站 |

其中**吞腿那个是端到端才暴露的**：单测只验了"景点集合不变"，没验"交通段条数不变"。
已补断言锁死。
